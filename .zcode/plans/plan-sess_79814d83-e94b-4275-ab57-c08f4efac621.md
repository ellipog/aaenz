# Fix: `bun dev` process explosion (keep Turbopack)

## Root cause
`dev` is bare `next dev` → Next 16 defaults to **Turbopack** → Turbopack forks child + native workers. Under **Bun on Windows** this is a known infinite-process-spawn bug ([bun #18113](https://github.com/oven-sh/bun/issues/18113) — "does not occur when using Node"; [next #77102](https://github.com/vercel/next.js/discussions/77102)). Your app code is clean — it's the toolchain. You're on Next `16.2.2`; `16.3` reduced Turbopack CPU/mem.

No public Turbopack worker-cap env var exists, so we remove the triggers. Turbopack stays.

## Changes (in order — test `bun dev` after each)

### 1. Clear stale dev cache + stray processes (cheap, often enough on its own)
A stuck HMR/compile loop in `.next` is a known spawn trigger.
- Delete `.next/`
- Kill any leftover `node.exe` from the last crash (Task Manager / `taskkill /F /IM node.exe`)

### 2. Primary fix — launch `next` under Node, not Bun's runtime (keeps Turbopack)
Edit `package.json`:
```json
"dev": "node ./node_modules/next/dist/bin/next dev",
```
Why: the spawn storm is Bun-runtime-specific. With this, you still type `bun dev` (Bun just orchestrates), but `next` itself runs under Node — dodging the Bun×Turbopack fork bug. Turbopack is still the bundler (Next 16 default). Dev speed is dominated by Turbopack, not the runtime, so you keep the speed without the crash.

### 3. Upgrade Next `16.2.2` → latest `16.3.x`
16.3 explicitly cut Turbopack CPU/memory. Reinforces step 2.
- `bun remove next && bun add next@^16.3` (or pin the exact latest 16.3 patch)
- Re-test `bun dev`.

### 4. Guard against a Turbopack root-detection compile loop (optional but recommended)
In commit `a8a0ac4` you deleted `turbopack: { root: __dirname }` because `__dirname` is undefined in ESM. The *correct* form is `import.meta.dirname` — restoring it prevents a known Turbopack infinite-compile loop. Edit `next.config.ts`:
```ts
const nextConfig: NextConfig = {
  reactStrictMode: true,
  turbopack: { root: import.meta.dirname },
};
```

## Verification
After the changes, run `bun dev` and confirm:
- Process count stays bounded (parent + ~1–3 workers), not hundreds.
- Dev server compiles and HMR works at `localhost:3000`.
- No new build errors from the Next bump.

## Fallback (if it still spawns)
Step 2 is the load-bearing fix. If a spawn returns, run `npm run dev` (or `npx next dev`) directly under Node — that definitively removes Bun from the equation while keeping Turbopack. We'd then know it's a pure Next/Windows Turbopack worker issue to chase separately.
